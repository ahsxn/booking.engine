### Data retrieval and ordering

Use one event query, conceptually:

```php
Event::query()
    ->select(['id', 'slug', 'title', 'cover_image_url', 'organizer_name', 'venue_name', 'venue_address', 'timezone', 'starts_at', 'ends_at'])
    ->with('ticketTypes:id,event_id,name,description,display_order,price_minor,currency')
    ->orderBy('starts_at')
    ->orderBy('id')
    ->get();
```

The existing relationship supplies ticket `display_order ASC, id ASC`; retain its parent matching `event_id` and primary key. No join duplicates, per-event queries, counts, status/capacity calculations, `whereHas` exclusion or speculative model scopes. All persisted events are public under the current seeded-only contract; events without ticket definitions remain visible. No publication flag exists.

Capture the reference instant **before** querying, partition in memory with `starts_at > reference` for upcoming and `<= reference` for past. Preserve ascending `(starts_at,id)` upcoming order; reverse the past partition to descending `(starts_at,id)` for most recently started first. Reindex both lists before serialization so empty and populated groups become JSON arrays. This costs at most two catalogue SELECTs for any nonempty catalogue, one when empty. The four-event seed makes full retrieval appropriate; no pagination/cache/query parameters are introduced. Projection includes the existing `slug` and `cover_image_url` needed by the public contract, while excluding unused event description and ticket capacity. `localStartDate` is derived after hydration, not selected as a stored column or extracted from the UTC timestamp in SQL. DTO conversion occurs only after eager loading.

### Inertia prop contract

Use camelCase explicitly in `toArray()`; never call a model's `toArray()` or pass raw models to Inertia. The page-specific payload is:

```ts
export type TicketTypeListing = {
    id: number;
    name: string;
    description: string | null;
    priceMinor: number;
    currency: 'GBP';
    priceLabel: string;
};

export type EventListing = {
    id: number;
    slug: string;
    title: string;
    coverImageUrl: string;
    localStartDate: string;
    organizerName: string;
    venueName: string;
    venueAddress: string;
    timezone: string;
    startsAt: string;
    endsAt: string;
    startsAtLabel: string;
    endsAtLabel: string;
    ticketTypes: TicketTypeListing[];
};

export type EventListingPageProps = {
    upcoming: EventListing[];
    past: EventListing[];
};
```

`slug` maps directly from `events.slug`; `coverImageUrl` maps directly from the existing `events.cover_image_url`, preserving the seeded data URL/reference without fetching, transforming or rendering it. `localStartDate` is a server-calculated event-local date string in `YYYY-MM-DD` format, e.g. `2027-01-01` for a Helsinki event starting at `2026-12-31T23:30:00Z`. All three are required strings on the DTO and every serialized event, even though Slice 1B does not use them for images, links or calendar UI.

`startsAt`/`endsAt` are UTC ISO-8601 strings from the immutable cast, e.g. `2027-01-16T12:00:00.000000Z`. Labels use event-zone `format('j F Y, H:i (P)')`, e.g. `16 January 2027, 14:00 (+02:00)`, with the IANA identifier displayed alongside the schedule. Server price labels are fixed English GBP, e.g. integer `1250` → `£12.50`, `1` → `£0.01`; use `intdiv`, remainder and zero padding, never floating-point division. `priceMinor` stays an integer; no totals are calculated.

Existing shared `name` and standard Inertia `errors` remain framework/shared props; do not redeclare or change them. Exact event/ticket whitelist tests must ensure no `capacity`, counts, availability/sold-out flags, event_id, audit timestamps, auth props, event description or unrelated relation fields leak. `slug`, `coverImageUrl` and `localStartDate` are explicit whitelist members. IDs remain list keys, not credentials; carrying a slug does not introduce a detail route or link.

### Upcoming/past and timezone policy

Instant comparisons are UTC; local wall dates are presentation only. Exactly at start, the event belongs in Past, including an event whose end is still future. Use one frozen request reference so events cannot fall into both/neither section around a clock boundary. No distinct ongoing label/status is invented. This is read-only presentation; later hold creation must independently enforce its authoritative deadline.

Convert each endpoint separately with `setTimezone($event->timezone)` on immutable date objects. Do not use `shiftTimezone`, strip the timezone, parse timezone-naive strings, or use the browser/app zone as a fallback. Both labels include full dates and each endpoint's numeric offset, so midnight/year boundaries, overnight spans and a DST change during the event remain unambiguous. Display the stored IANA name as well as offsets rather than relying on an ambiguous abbreviation. Compute `localStartDate` in `EventListingData::fromModel()` as `$event->starts_at->setTimezone($event->timezone)->format('Y-m-d')`, using the event's stored IANA timezone. It is a date-only `YYYY-MM-DD` string with no offset/time suffix and must not come from the UTC date, browser clock/timezone or application timezone. The immutable conversion preserves the stored instant. This slice has no calendar-month grouping; Slice 2 can use this server-provided local date for grouping without reinterpreting UTC dates.

## 6. State transitions and transaction protocol

No business state transition, explicit read transaction, row lock, lock order, deadlock retry, reservation write, payment protection or distributed coordination is applicable to listing. At each request an event is projected into a group; this is not a persisted status transition. Classification and formatting do not update timestamps or rows.

Eager loading uses ordinary short SELECTs under existing PostgreSQL isolation. Two SELECTs do not promise an atomic catalogue snapshot across concurrent CLI edits; a listing is advisory and makes no inventory guarantee. That is acceptable for seeded-only read content. Do not add repeatable-read transactions or locks for this slice. Concurrent GETs and a lost response can safely be retried; catalogue state stays unchanged. Existing session/cache/throttle middleware may make infrastructure writes; “read-only” refers to event/ticket/business data, not a promise to disable that middleware.

Development migration/seed operations are separate CLI preparation, with their existing migration/seed transaction semantics. No Stripe call, scheduled coordination or job/webhook flow exists. The 1,000-way scarce-inventory harness and crash-at-payment-commit tests are not applicable until capacity-changing slices; no reliability claim about those paths is made here.
