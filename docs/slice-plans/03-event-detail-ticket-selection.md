No new money value object or selection DTO is needed: existing integer minor-unit GBP fields supply the React calculation. No repository, service interface, inventory abstraction or generic response layer. No Form Request is proposed: slug binding handles the detail GET's only input, and quantities are never submitted in this slice.

**Only server path:** GET → slug binding → ShowEventController → ShowEvent → existing Event/ticket relation → EventDetailData → Inertia. The server supplies catalogue data, not a validated selection or an authoritative checkout quote. There is no persistence stage.

Detail event type is `EventListing & { description: string; selectionOpen: boolean; ticketTypes: TicketTypeListing[] }`. Global cutoff is distinct from ticket stock; frontend must label already-started events “Registration closed”, never Sold out. `selectionOpen` is computed at detail load for presentation only. This slice adds no server-side selection/cutoff enforcement, polling or deadline timer. Do not add an availability field or live Available label. Genuine Sold out behaviour remains deferred to Slice 4 by owner decision.

Local calculation follows the event's existing ticket order. For each known ticket, `lineTotalMinor = quantity × priceMinor`; `totalQuantity` and `totalMinor` are sums of those lines. Keep calculations in integer minor units and format only for display using `Intl.NumberFormat('en-GB', { style: 'currency', currency: 'GBP' })` with two decimals. Example Lantern Pages: 2 × 1500 + 1 × 2200 = 5200 → **£52.00**. Initial total is £0.00. No fees are added. Unit prices remain the server-provided priceLabel; React formats derived line/combined totals consistently.

Show “Total” with a visible qualification: “Based on listed prices. Price and availability will be checked at checkout.” This is a local display, never “server checked”, an authoritative quote or a reservation. Prices remain those supplied at page load until normal navigation/reload supplies new props. Slice 4 will validate submitted IDs/quantities, reprice from PostgreSQL, enforce capacity/cutoff and atomically create the hold; it must never trust the browser total.

404 for unknown slug; existing 429 rate limiting and ordinary 5xx error behaviour for detail loads. Preserve the existing feed when client navigation fails. There are no selection-validation responses, transport errors or retries to handle.

## 5. Database and migrations

**No schema changes are genuinely necessary for this proposal.** Existing event description, UTC timestamps, IANA zone, public venue, organizer name and cover URL cover the product detail fields. Existing ticket name/description/display_order/price_minor/currency supply local selection and total display. Current unique event slug, ticket `(event_id,code)` uniqueness and `(event_id,display_order,id)` index support lookup/order. Positive GBP price and capacity constraints remain unchanged. No backfill, status column, index, inventory counter or rollback procedure is introduced.

The current schema cannot prove Sold out. Adding `is_sold_out`, setting capacity 0 or manufacturing confirmed sales would change semantics or weaken approved constraints. The owner approved: no live Available label/availability field, no genuine Sold out behaviour until Slice 4, and “Registration closed” only for started-event presentation. Current tickets show names and catalogue prices without stock claims. Complete inventory-derived A03 evidence remains deferred. No schema change is authorized by this limitation.

No stored states/counters change. The detail action computes selectionOpen from UTC server time for initial presentation. Quantities and derived totals exist only in React memory. Database constraints protect catalogue validity; React constrains normal interactions to nonnegative integers and ten combined tickets. These UI limits are not a security boundary. Server-side selection validation, authoritative pricing, capacity enforcement and hold creation are deferred entirely to Slice 4.

## 6. State transitions and transaction protocol

**Domain transactions, locks, global lock order, deadlock retries and release/confirmation transitions: Not applicable.** The only action, ShowEvent, reads existing catalogue rows. It performs no selection validation, capacity mutation, order creation, Stripe call or scheduled/webhook coordination. No DB::transaction or lockForUpdate is needed; this slice must not invent Slice 4's global locking protocol.

Selection transitions are 0→1→…→10 and back, per type subject to the combined cap. Every permitted change immediately derives fresh local line/combined totals from the detail props. These are UI transitions, not durable order states. Get Tickets never transitions to pending/success or creates anything. Reload or process loss discards only local selection state. Stale catalogue prices cannot create an incorrectly priced order here because there is no order. Slice 4 must validate and reprice selections under its separately approved hold transaction design.
